## Overview

**textkit** is a small Python utility library providing pure text-transformation functions: `slugify`, `truncate`, `title_case`, `snake_case`, `collapse_whitespace`, and `fold_accents`. It lives in a sandbox repository (`dardant/tv-sandbox`) used for validating TandemVelocity end-to-end against real providers. The repository itself is described as disposable and non-production, but textkit is consumed by at least two downstream services (a CMS importer and a file-naming service), so it is treated with care regarding API stability and backward compatibility.

## Interfaces and integrations

Two known consumers depend on textkit:

1. **CMS importer** — depends on hyphenated slugs (from `slugify`) and the three-dot ellipsis (from `truncate`).
2. **File-naming service** — depends on the published function names exported via `textkit.__all__`.

Consumer contract tests for both live in the `ci/` directory and run in CI only (not locally). The public API surface is defined by `textkit.__all__` in `src/textkit/__init__.py` and mirrored in `ci/public_api.txt`.

CI is GitHub Actions. There is no deployment configuration in the repository; textkit is a library, not a deployed service.

## Conventions

- **Language & runtime**: Python 3.10+, standard library only — no third-party dependencies. Every module begins with `from __future__ import annotations`.
- **Build system**: `pyproject.toml` (Python pyproject-based build).
- **Public API**: Defined by `textkit.__all__` in `src/textkit/__init__.py`. Adding a function requires exporting it there and adding its name to `ci/public_api.txt`.
- **Test layout**: One `tests/test_<module>.py` per source module, co-located by behaviour. Bug fixes must include a test that fails before the fix.
- **Local testing**: `pytest -q`. CI additionally runs `pytest -q ci` (consumer contract tests) and a changelog check.
- **Changelog discipline**: Every change must add a line under `## Unreleased` in `CHANGELOG.md` in the appropriate subsection (`Added`, `Changed`, `Fixed`). CI enforces this — branches that don't touch `CHANGELOG.md` fail.
- **Breaking changes**: Removing or renaming a published name is breaking. If a consumer contract test in `ci/` would need editing to pass, the change is breaking and requires a maintainers' decision. Contract tests must never be edited to accommodate a change.
- **CI checks (GitHub Actions)**: Unit tests on Python 3.10 and 3.12, consumer contract tests, changelog presence check, and public API consistency check.

## Architecture constraints and fragile areas

1. **`slugify` output format**: The CMS importer depends on slugs being hyphen-separated. Any change to the separator character or slug normalization logic (e.g., accent folding behaviour) would break that consumer. The contract test in `ci/` guards this.

2. **`truncate` ellipsis marker**: The CMS importer depends on the three-dot ellipsis (`...`). Changing the truncation marker (e.g., to `…` Unicode ellipsis) would be a breaking change.

3. **Published names in `textkit.__all__`**: The file-naming service depends on the exact exported function names. Renaming or removing any function is breaking. The `ci/public_api.txt` file and its corresponding contract test guard this, but the guard is only as strong as CI enforcement — local `pytest -q` does not run these checks.

4. **`ci/public_api.txt` drift**: If a developer adds a function to `__all__` but forgets to update `ci/public_api.txt` (or vice versa), the contract test should catch it, but the integrity depends on the CI job being correctly configured.

5. **No declared test command in findings**: TandemVelocity's scan found no test commands in the build configuration (`tests=[]`), even though `pytest -q` is documented. This suggests the test invocation may not be formally declared in `pyproject.toml`, relying on convention and CI workflow definitions instead.
